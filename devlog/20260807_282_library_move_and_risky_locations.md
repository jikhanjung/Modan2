## 불변식 하나로 설계했다

**전부 옮겨졌거나, 원본이 손도 안 댄 상태로 남아 있거나 — 그 사이는 없다.**

계획서 위험 1(부분 이전)이 이 기능이 막으려는 실패다. 두 폴더에 절반씩 있고
사용자는 어느 쪽이 진짜인지 모른다. 그래서 흥미로운 단언은 "파일이 도착했다" 가
아니라 **"이 실패 뒤에도 원본이 온전하다"** 이고, 테스트도 그쪽에 몰려 있다.

이동 수단이 볼륨에 따라 갈리고 **실패하는 방식이 서로 다르다**:

| | 같은 볼륨 | 다른 볼륨 |
|---|---|---|
| 방법 | 멤버별 `os.rename` | 전부 복사 → 전부 검증 → 그다음 삭제 |
| 실패 시 | 이미 옮긴 것을 되돌린다 | 원본은 애초에 안 건드렸다 |
| 취소 | 중간이라는 게 없다 (메타데이터만) | 삭제에 도달하지 않는다 |

**취소를 "복사한 것을 되돌린다" 로 구현하지 않았다** — 계획서가 지시한 대로
"원본을 지우지 않는다" 로 안전을 확보한다. 복사–검증–삭제 순서 자체가 그 보장을
공짜로 준다.

멤버 순서는 `backups` 가 선두다. 복구 수단이므로 새 위치에서 가장 먼저 온전해야
하고 옛 위치에서 가장 나중에 사라져야 한다.

`temp/` 는 멤버가 아니고(진짜 임시 파일), **사용자가 그 폴더에 둔 다른 파일도
멤버가 아니다.** 쓸어 담지 않고 남기며, 그래서 폴더 자체도 살아남는다.

## 계획서와 달라진 점 — 로그 파일

계획서 2단계는 "DB는 열려 있으므로 닫고 옮긴 뒤 `set_database_path()` 로 다시
연다" 만 다룬다. **로그 파일이 빠져 있었는데, 계획서가 쓰인 시점에는 로그가 데이터
디렉터리를 따라가지 않았기 때문이다** — 1단계 도중에 바뀐 결정이다
(`get_log_directory` docstring 참조).

열린 로그 파일은 Windows에서 폴더 rename 을 거부시키고, rename 이 성공하는
플랫폼에서도 핸들러가 없어진 경로에 계속 쓴다. `mu.detach_log_file()` /
`attach_log_file()` 을 추가해 이동 전후로 감쌌다. 파일 이름은
`mu.log_file_name()` 하나로 모으고 `main.setup_logging` 도 그걸 쓰게 했다 —
두 곳에서 따로 만들면 "로그가 어느 파일인지" 가 갈라지기 시작한다.

`attach_log_file` 에서 **빈 리스트와 `None` 을 구별해야 한다.** 처음엔
`detached or [기본값]` 으로 썼는데, 그러면 "열린 파일 핸들러가 없었다"(`[]`)가
"하나 새로 열어라" 로 둔갑한다. 테스트가 이걸 잡았다 — 콘솔 전용으로 도는 pytest
런에서 개발자의 실제 로그 디렉터리에 파일을 만들 뻔했다.

## `--db` 를 끌고 가지 않는다

`--db` 는 파일을 직접 지목하고 데이터 디렉터리와 독립이다. 이동 후 무조건
`set_database_path(mu.get_database_path())` 를 부르면 **시작할 때 지정한 것과 다른
DB로 갈아탄다.** 그래서 현재 DB가 source 안에 있을 때만 닫고 다시 연다.

## 라이브 재바인딩이 가능한 이유 — 1단계의 배당금

이동 후 재시작 없이 계속 쓸 수 있다. 이게 되는 것은 **1단계가 모든 경로 캐싱을
없앴기 때문** 이다. 첨부 경로는 호출 시점에 `mu.get_storage_directory()` 로
해석되므로, 전역 하나를 바꾸면 메모리에 있는 모델 인스턴스까지 전부 새 위치를
본다. import 시점 기본 인자가 남아 있었다면 이 기능은 재시작을 강요했을 것이다.

## 위험한 위치 — 경고이지 금지가 아니다

`describe_location_risk()` 는 경로 **컴포넌트 단위** 로 이름을 맞춘다. "boxes"
폴더가 "Box" 로 잡히면 안 되기 때문이다. `OneDrive - Contoso University` 처럼
접미사가 붙는 실사용 형태를 위해 접두 일치도 본다. UNC 경로는 어디서나 알아보고,
매핑된 Windows 드라이브 문자는 `GetDriveTypeW` 로 OS에 묻는다.

**금지하지 않는다.** 사용자 디스크이고 감수할 이유가 있을 수 있다. 다만 기본
버튼은 안전한 쪽("다른 폴더 고르기")이고 위험한 쪽은 일부러 골라야 한다.

메시지가 "권장하지 않습니다" 로 끝나지 않게 했다 — 그건 아무것도 가르쳐 주지
않는다. 실제 실패 두 가지(기록 중 업로드, 두 머신에서 조용히 갈라지는 사본)와
대안(백업·내보내기를 대신 넣으라)을 말한다. 테스트가 그 세 요소의 존재를 단언한다.

## 테스트

`tests/test_data_directory_move.py` 39개 + 다이얼로그 쪽 추가. 전체 1995 passed,
10 skipped (이전 1948 + 47).

다이얼로그 테스트에서 두 번 미끄러질 뻔했다:

1. **source 가 `mu.get_data_directory()` 이므로 기본값이면 개발자의 실제 데이터
   디렉터리다.** 기존 테스트가 정확히 그 상태로 이동 제안을 받고 있었다 —
   devlog 278 과 같은 사고를 이번엔 "테이블 삭제" 가 아니라 "이동" 으로 낼 뻔한
   자리다. `library` 픽스처로 `_configured_data_directory` 를 tmp 로 돌려놓았다.
2. **`monkeypatch` 는 `MdModel.database_path` 는 되돌리지만 `gDatabase.init()` 은
   되돌리지 않는다.** 이동 테스트가 peewee 바인딩을 tmp 파일에 남기면 세션의
   나머지가 pytest 가 지운 파일을 질의한다. `restore_database_binding` 픽스처
   추가.

`answering()` 헬퍼로 여러 버튼 QMessageBox 를 라벨로 답한다. 역할이 아니라 **보이는
라벨** 로 맞추므로 버튼 이름을 바꾸면 테스트가 깨진다 — 그게 의도다.
