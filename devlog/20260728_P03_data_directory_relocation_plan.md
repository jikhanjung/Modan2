# 데이터 디렉터리 계획 — 설정 가능하게, 그리고 백업 가능하게

## 날짜
2026-07-28 (2026-07-29 개정)

## 개정 (2026-07-29) — 기본값은 옮기지 않는다

초안의 4단계는 기본값을 `<Documents>/PaleoBytes/Modan2` 로 바꾸는 것이었다.
**그 단계를 철회하고 "라이브러리 백업" 으로 대체한다.** 1·2단계는 그대로다.

근거는 아래 배경·조사 7·8·위험 5에 반영했고, 요지는 셋이다.

1. **Zotero 선례.** 연구용 도구 + SQLite + 첨부 저장소라는 구조가 사실상 동일한데
   기본값이 `~/Zotero` — 프로필 루트다. 관례를 몰라서가 아니라
   "`zotero.sqlite` 를 동기화 폴더에 두지 말라" 를 공식 문서로 경고하면서 내린
   선택이고, 백업은 자체 동기화 서비스로 따로 푼다. 같은 제약에서 나온 같은 답이다.
2. **트레이드의 방향이 나쁘다.** 백업 안 됨은 드물게·시끄럽게 실패한다(디스크가
   죽고 사용자가 즉시 안다). 동기화 폴더의 SQLite는 상시로·조용하게 실패한다 —
   두 머신에서 같은 라이브러리를 열면 OneDrive는 병합하지 않고 충돌 사본
   (`Modan2-DESKTOP-XYZ.db`)을 만들고, 사용자는 한동안 모르며 알았을 때는 어느
   쪽이 진짜인지 판단할 수 없다. 연구 데이터에서는 조용한 실패가 더 나쁘다.
3. **스냅샷은 동기화에 안전하고 라이브 DB는 아니다.** 배경의 구체적 피해는
   "백업이 없음" 이지 "위치가 관례에 안 맞음" 이 아니었다. 그 피해의 답은 살아
   있는 DB를 동기화 폴더로 옮기는 것이 아니라, 사용자가 아무 데나 — OneDrive
   포함 — 둘 수 있는 자족적 아카이브를 만들어 주는 것이다.

## 배경

`~/PaleoBytes/Modan2/` 는 세 플랫폼 어디의 관례도 아니다(devlog 276). 프로필
루트는 알려진 폴더가 놓이는 자리이지 앱 데이터 자리가 아니다.

관례 위반 자체보다 **구체적 피해가 하나 있다**: OneDrive의 Known Folder Move는
Documents·Desktop·Pictures를 백업하지만 프로필 루트의 임의 폴더는 백업하지
않는다. 사용자는 자기 파일이 클라우드에 있다고 믿는데 **연구 데이터의 유일한
사본만 백업에서 빠진다.**

**개정 후에도 이 피해 인식은 유효하다. 바뀐 것은 대응 수단이다** — 위치를 옮겨
남의 백업에 얹히는 대신, 이 앱이 직접 백업을 만든다(4단계). 관례 위반은 남지만,
Zotero라는 선례가 있는 이상 그 자체로 데이터를 위험에 빠뜨릴 값어치가 없다.

## 조사 결과 — 예상보다 훨씬 간단하다

계획을 세우기 전에 코드를 확인했고, **가장 큰 위험으로 꼽았던 것이 존재하지
않는다는 것** 을 발견했다.

### 1. 미디어 경로는 저장되지 않고 계산된다 ★

`MdImage.get_file_path()` (`MdModel.py:1022`) 와 `MdThreeDModel.get_file_path()`
(`:1233`) 는 이렇게 생겼다:

```python
def get_file_path(self, base_path=mu.DEFAULT_STORAGE_DIRECTORY):
    return os.path.join(
        base_path, str(self.object.dataset.id),
        str(self.object.id) + "." + self.original_path.split(".")[-1]
    )
```

**경로가 DB에 없다.** `base_path` + 데이터셋 id + 객체 id + 확장자로 매번
조립한다. `original_path` 는 사용자가 *가져온 원본 파일의 출처 기록* 일 뿐이고
(`:1074`, `:1251` 에서 `self.original_path = fullpath`), 저장 위치를 찾는 데는
확장자만 쓰인다.

따라서 **DB 재작성이 필요 없다. 이전은 디렉터리 트리를 옮기는 것이 전부다.**
이것이 이 작업 전체의 난이도를 결정한다.

### 2. 기본 인자는 import 시점에 고정된다 ★ (함정)

위 시그니처의 `base_path=mu.DEFAULT_STORAGE_DIRECTORY` 는 **모듈 import 때 한 번
평가된다.** 런타임에 `mu.DEFAULT_STORAGE_DIRECTORY` 를 바꿔도 이 기본값은 바뀌지
않는다. `tests/test_mdmodel.py:4460` 이 이미 이 점을 주석으로 남겨 두었다.

**센티넬은 선호가 아니라 필수다.** 처음에는 "호출부를 다 고치는 것보다 안전해서"
권했는데, 검토(2026-07-28) 후 호출부를 전수 조사하니 근거가 훨씬 강했다.

기본값을 가진 함수는 5개(`add_file`, `get_file_path` ×2, `get_original_file_path`,
`has_archived_original`)인데 **호출부가 이미 두 갈래로 갈라져 있다.**

| | 경로를 명시 | import 시점 기본값에 묶임 |
|---|---|---|
| 개수 | 9곳 | **14곳** |
| 어디 | `MdUtils`(3), `ModanController`(4), 두 뷰어(2), `object_dialog`(2) | `MdModel` 내부(11), `export_dialog`(3) |

그리고 **갈라진 방향이 최악이다.** 명시적인 쪽은 대체로 *읽기* 이고, 기본값에
묶인 `MdModel` 내부 11곳은 전부 *쓰기·삭제·복사* 다:

- `:607, :629, :636` — `add_file` (파일 기록)
- `:620` — 교체 시 옛 파일 **삭제**
- `:656, :672` — 객체가 데이터셋을 옮길 때 미디어 이동(원본 읽기 + 대상 쓰기)
- `:943, :947, :949` / `:1203, :1212` — 이미지·3D 모델 복제

즉 설정 가능화를 켜는 순간 **읽기는 새 위치를, 쓰기는 옛 위치를 보게 된다.**
`export_dialog.py:404-407` 도 기본값이라 내보내기가 이미지를 못 찾는다.

지금 증상이 안 보이는 이유는 `Modan2.py:568` 이 `storage_directory` 를 무조건
기본값으로 덮어쓰기 때문이다. **1단계가 그 덮어쓰기를 없애는 작업이므로, 1단계를
하는 순간 이 불일치가 잠재 버그에서 실제 버그가 된다.**

### 3. DB 경로에는 이미 올바른 선례가 있다

`MdModel.set_database_path()` (`:199`) 가 peewee의 제약을 정확히 다룬다 — 모델이
import 시점에 `gDatabase` 에 바인딩되므로 `database_path` 재할당만으로는 부족하고
`gDatabase.init()` 을 호출해야 한다. 주석에도 적혀 있다. 저장소 경로도 같은
성격의 문제이므로 이 함수를 본보기로 삼는다.

### 4. 로그는 설정을 읽기 전에 필요하다 (부트스트랩 문제)

`main.py:98` 이 `DEFAULT_LOG_DIRECTORY` 로 로깅을 세팅하는데, 이 시점은 설정
파일을 읽기 **전** 이다. 로그 위치를 사용자 설정에 따르게 하려면 초기 로그를
버리거나 이중 초기화를 해야 한다. **로그는 설정 대상에서 제외한다.**

### 5. 경로 정의가 또 중복돼 있다

`migrate.py:13` 이 `os.path.join(mu.DEFAULT_DB_DIRECTORY, "Modan2.db")` 로 DB
경로를 독립적으로 조립한다. `MdModel.py:194` 와 같은 값이지만 별개 정의다.
devlog 272에서 설정 경로가 두 곳에 정의돼 load/save가 어긋났던 것과 **정확히 같은
구조** 다. 이번에 합친다.

### 6. `storage_dir` 을 받고 버리는 함수가 이미 있다

`MdUtils.serialize_dataset_to_json()` (`:578`) 는 `storage_dir` 파라미터를 받고
docstring에 설명까지 달아 놓은 뒤, `:591` 에서

```python
os.path.abspath(storage_dir or _get_storage_dir())
```

을 **대입 없이 평가하고 버린다.** 함수 본문 어디에서도 `storage_dir` 을 쓰지
않는다. ZIP 내보내기의 스키마 직렬화 경로다.

ruff의 B018(무의미한 표현식)은 함수 호출을 부작용 가능성 때문에 통과시키므로
잡히지 않았다. 위 조사 2와 같은 계열 — **경로를 바꿀 수단이 있는 척하지만 실제로는
존중하지 않는 코드** 다. 1단계에서 함께 정리한다.

### 7. `backups/` 는 DB만, 그것도 같은 디스크에 백업한다 ★ (2026-07-29 추가)

`MdModel.prepare_database()` (`:2645-2670`) 는 `Modan2.db` 를 날짜별로
`backups/` 에 복사하고 10개를 유지한다. **`data/` 의 이미지·3D 모델은 대상이
아니다.** 그리고 사본이 원본과 같은 디스크에 있다.

즉 현재 백업 체계는 **DB 손상에는 대비되지만 디스크 손실에는 무력하고, 원본
미디어는 어느 쪽에도 대비가 없다.** 초안은 "한 폴더 복사가 곧 완전한 백업" 을
beta.2가 확보한 성질로 전제했는데, 그 성질은 사용자가 직접 폴더를 복사할 때만
성립하고 앱이 스스로 하는 일은 절반뿐이었다.

**이것이 4단계를 백업 기능으로 바꾼 직접적 근거다.** 배경이 지적한 피해는 위치
문제로 위장한 백업 문제였다.

### 8. SQLite는 rollback journal 모드다 (2026-07-29 추가)

`gDatabase = SqliteDatabase(database_path, pragmas={"foreign_keys": 1})`
(`:196`) — WAL을 켜지 않았으므로 기본값인 rollback journal 이다.

동기화 관점에서는 오히려 다행이다. WAL은 `-wal`/`-shm` 이 본체와 항상 정합해야
해서 동기화 클라이언트가 서로 다른 시점에 올리면 깨지는 것이 보장되는데,
rollback journal 은 트랜잭션 중에만 `-journal` 이 존재하고 그 사이에는 DB 파일이
자족적이다. **다만 이것은 위험 5를 줄일 뿐 없애지 않는다** — 충돌 사본 문제
(개정 근거 2)는 저널 모드와 무관하다.

향후 성능 목적으로 WAL을 켜게 되면 **이 계획의 판단을 다시 봐야 한다.**

## 설계 — 부트스트랩이 구조를 결정한다

데이터 위치를 설정 가능하게 만들면 곧바로 문제가 생긴다: **설정 파일이 데이터
디렉터리 안에 있으면, 데이터 디렉터리를 알기 위해 설정을 읽어야 하고 설정을 읽기
위해 데이터 디렉터리를 알아야 한다.**

devlog 272는 "사용자가 소유한 모든 것을 한 디렉터리에" 라는 근거로
`preferences.json` 을 데이터 디렉터리에 넣었다. **그 결정을 부분적으로 되돌려야
한다.** 다행히 되돌리는 방향이 관례상 더 옳다:

| 무엇 | 성격 | 위치 |
|---|---|---|
| 설정, 로그, temp | 앱 데이터 — 잃어도 복구 가능, 머신 로컬 | OS 앱 데이터 위치 (고정) |
| DB, 미디어, 백업 | 사용자 문서 — 유일한 사본, 백업 대상 | `~/PaleoBytes/Modan2/` (기본값 유지, **설정 가능**) |

**(2026-07-29 개정)** 데이터 행의 기본값은 원래 Documents 였다. 개정 근거 2·3에
따라 현행 위치를 유지한다. **"설정 가능" 이 이 표의 핵심이고 그 부분은 그대로다** —
Documents를 원하고 자기 동기화 상황을 아는 사용자는 스스로 지정하면 된다. 그
정보는 어차피 우리에게 없다.

이 분리가 Microsoft의 LocalAppData 의미론과도 맞는다. LocalAppData는 *잃어도
살아남는* 데이터의 자리다. 설정은 그렇지만 연구 데이터는 아니다.

### 경로 결정

**`platformdirs` 로 해석한다.** `expanduser("~")` 에 `"Documents"` 를 붙이는 식의
조립은 한국어 Windows의 `문서`, 리디렉션된 알려진 폴더(OneDrive가 Documents를
자기 폴더로 옮긴 경우가 흔하다), 플랫폼 차이에서 전부 깨진다.

**Qt의 `QStandardPaths` 를 쓰지 않는다** — 초안은 Qt를 전제했는데 바꿨다. 두 가지
이유가 있다.

1. **초기화 순서.** `MdUtils` 는 `main.py` 가 `QApplication` 을 만들기 전에
   import된다(로깅이 먼저 구성된다). Qt의 앱별 위치는 조직명·앱명에서 파생되는데
   그 시점에는 설정돼 있지 않아, 즉시 평가하면 **다른 모든 애플리케이션과 공유하는
   설정 루트** 가 조용히 나온다(실측 확인: 이름 설정 전 `~/.config`, 설정 후
   `~/.config/PaleoBytes/Modan2`). `platformdirs` 는 순수 파이썬이라 이 순서
   의존이 없다.
2. **macOS 관례.** Qt는 `~/Library/Preferences` 로 보내지만 Apple은 그곳을
   plist/defaults 시스템의 자리로 두고 있다. 앱이 직접 관리하는 JSON은
   `~/Library/Application Support` 가 맞고, `platformdirs` 가 그쪽을 준다.

| 무엇 | 해석 | Windows | macOS | Linux |
|---|---|---|---|---|
| 설정 | `platformdirs.user_config_dir()` + 벤더 | `%LOCALAPPDATA%\PaleoBytes\Modan2` | `~/Library/Application Support/PaleoBytes/Modan2` | `~/.config/PaleoBytes/Modan2` |
| 데이터 | `DocumentsLocation` 상당 + 벤더 | `<Documents>/PaleoBytes/Modan2` | 〃 | 〃 |
| 로그 | **옮기지 않는다** | 데이터 디렉터리 안 | 〃 | 〃 |

Linux 값은 실행해 확인했고, Windows/macOS는 `platformdirs` 소스에서 확인했다
(`windows.user_config_dir` → `CSIDL_LOCAL_APPDATA`, `macos` →
`~/Library/Application Support`).

**벤더 디렉터리는 직접 붙인다.** `platformdirs` 는 `appauthor` 를 macOS·Linux에서
무시한다 — 그쪽 관례에 벤더 계층이 없기 때문이다. 하지만 이 앱이 소유한 다른 모든
경로(설치 디렉터리, 시작 메뉴, 데이터 디렉터리)가 `PaleoBytes` 아래로 묶여 있으므로,
**설정만 세 플랫폼 중 둘에서 갈라지는 것이 관례를 조금 넘어서는 것보다 나쁘다.**
벤더 계층이 금지된 것이 아니라 필수가 아닐 뿐이다.

**로그는 옮기지 않는다.** 조사 4의 부트스트랩 문제(설정을 읽기 전에 로깅이
구성된다)도 있지만, 더 실질적인 이유는 **문제를 조사할 때 로그가 데이터와 같은
폴더에 있어야 한 곳만 보면 되기 때문** 이다.

### 설정을 Roaming 에 두지 않는 이유

설정 파일은 1KB도 안 되므로 Windows의 `%APPDATA%`(Roaming)가 교과서적으로는
맞다 — devlog 272가 130MB 프로그램 본체를 Roaming에서 뺀 것과 모순되지 않는다.
그래도 Local을 고른 이유가 둘이다.

1. **`SettingsWrapper.setValue` 가 변경할 때마다 즉시 저장한다**(`Modan2.py:203`
   의 `save()` 는 모든 `setValue` 에서 호출된다). 창을 옮길 때마다 파일이 다시
   쓰이므로, 동기화 폴더에 두면 불필요한 sync churn 이 생긴다.
2. **내용의 대부분이 머신별 상태다** — 9개 창의 지오메트리와 최대화 플래그.
   실험실 데스크톱과 노트북은 화면 구성이 다르니 로밍은 이득보다 성가심이 크다.
   언어·색상 정도는 로밍될 값어치가 있지만, 그것 때문에 파일을 둘로 쪼개는 것은
   1KB짜리 페이로드에 과하다.

### 조직명에 대한 메모

2026-07-28에 `main.py` 의 `setOrganizationName` 을 `"Modan2 Team"` 에서
`COMPANY_NAME`(=`PaleoBytes`)으로, 앱명도 `PROGRAM_NAME` 으로 통일했다
(`d36a319`). 당시에는 `QStandardPaths` 가 이 이름들로 경로를 만들기 때문에

## 구현 단계

### 1단계 — 저장 위치를 설정 가능하게 (기본값 변경 없음)

**이 단계만으로도 실질적 피해가 크게 줄어든다** — 관례에 맞지 않는 기본값이어도
원하는 사람은 옮길 수 있다. 그리고 이전 작업 자체가 이 기능 위에서 이뤄진다.

- `MdUtils` 에 현재 저장소 경로를 돌려주는 단일 조회 함수. `get_storage_directory()`
  가 이미 비슷한 일을 한다(`MdUtils.py:571`, `m_app.storage_directory` 를 보고
  없으면 기본값) — 이걸 정식 진입점으로 승격하고 설정 파일을 읽게 한다.
- `MdModel` 의 `base_path=mu.DEFAULT_STORAGE_DIRECTORY` 기본값 4곳을 `None`
  센티넬로 교체(위 함정 2).
- **죽은 UI를 살린다**: `dialogs/preferences_dialog.py:859` `select_folder` 는
  "legacy method" 이고 그것이 쓰는 `edtDataFolder` 위젯은 **생성되는 곳이 없다.**
  고른 경로는 다이얼로그 인스턴스에만 남고 `Modan2.py:568` 이
  `m_app.storage_directory` 를 무조건 덮어쓴다. 위젯을 만들고 `preferences.json`
  에 저장하고 `Modan2.py:568` 이 설정값을 존중하게 한다.
- `migrate.py:13` 의 중복 DB 경로 정의를 제거(위 5).
- `serialize_dataset_to_json` 의 버려지는 `storage_dir` 을 실제로 쓰게 하거나
  파라미터를 없앤다(위 6).

**테스트 — 쓰기만이 아니라 읽기·삭제·복사까지 덮을 것.** 조사 2에서 갈라진 방향이
"읽기는 새 위치, 쓰기는 옛 위치" 였으므로, 첨부만 확인하면 정확히 그 버그를
놓친다. 저장소를 tmp_path로 지정하고:

- 이미지 첨부 → 지정한 곳에 생기는지
- **조회** → 뷰어/컨트롤러 경로가 같은 곳을 보는지
- **객체를 다른 데이터셋으로 이동** (`MdModel:656/672`) → 미디어가 따라가는지
- **이미지 교체** (`:620`) → 옛 파일이 지정한 저장소에서 지워지는지
- **데이터셋 복제** (`:943`, `:1203`) → 사본이 지정한 저장소에 생기는지
- **내보내기** (`export_dialog`) → 이미지를 찾는지
- 재시작(설정 재로드) 후에도 전부 성립하는지

### 2단계 — 이전 기능

**사용자가 명시적으로 실행하는 동작으로 만든다.** 자동 이동은 안 된다 — 수 GB를
옮기는 도중 실패하면 데이터가 두 곳에 흩어진다.

Preferences에서 위치를 바꾸면 묻는다: "기존 데이터를 새 위치로 옮길까요?"

알고리즘:
1. 대상이 비어 있는지 확인. 아니면 거부.
2. **여유 공간 확인** (`shutil.disk_usage`). 부족하면 시작하지 않는다.
3. **백업(`backups/`)을 먼저 옮기고 검증한다.** 그다음 DB와 미디어.
   백업을 데이터 디렉터리 안에 두기로 했으므로(설계 참조) 순서를 잘못 잡으면
   데이터와 그 복구 수단이 한 사건으로 같이 위험해진다. 백업이 먼저 새 위치에
   온전히 있으면 이후 구간에서 실패해도 복구 경로가 남는다.
4. 같은 볼륨이면 `os.rename` (원자적, 즉시). 다른 볼륨이면 복사 후 검증 후 삭제.
5. 진행 표시 + 취소 가능.
6. **원본은 검증 전까지 지우지 않는다.** 파일 개수와 크기를 대조한 뒤에만 삭제.
7. 설정의 경로는 **이전 성공 후에** 갱신한다. 순서가 반대면 실패 시 앱이 빈
   디렉터리를 가리킨 채 시작한다.

DB는 열려 있으므로 닫고 옮긴 뒤 `set_database_path()` 로 다시 연다(선례 3).

**테스트**: 같은 볼륨/다른 볼륨, 대상이 비어 있지 않음, 공간 부족, 중간 실패 시
원본 보존, 이전 후 이미지가 여전히 열리는지.

### 3단계 — 설정을 OS 설정 위치로 ✅ **완료 2026-07-28**

devlog 272가 데이터 디렉터리에 모아 놓은 `preferences.json` 을
`platformdirs.user_config_dir()` + `PaleoBytes/Modan2` 로 옮겼다.
마이그레이션은 자동 — 1KB 미만이고 실패해도 창 위치가 초기화될 뿐이다. 이전
위치 두 곳(`~/PaleoBytes/Modan2/preferences.json`,
`~/.modan2/config.json`)을 최신 순으로 확인하고 원본은 남긴다.

**로그는 옮기지 않았다.** 조사 4의 부트스트랩 문제도 있지만, 실질적인 이유는
문제를 조사할 때 로그가 데이터와 같은 폴더에 있어야 한 곳만 보면 되기 때문이다.

**이 단계를 먼저 한 것은 순서상 옳았다.** 원래 초안은 이걸 마지막에 뒀는데
**뒤집혀 있었다.** 1단계의 전제는 "설정 파일 위치는 아직 고정" 이고 그 고정
위치는 데이터 디렉터리 안이었다. 당시 4단계였던 기본값 변경을 설정 이전보다 먼저
하면 신규 설치가:

- 데이터 → `<Documents>/PaleoBytes/Modan2`
- 설정 → `~/PaleoBytes/Modan2/preferences.json`

이 되어, **없애려던 그 디렉터리를 `preferences.json` 하나 담으려고 새로 만든다.**

**(2026-07-29)** 기본값 변경이 철회되면서 이 순서 논증의 대상은 사라졌다. 그래도
이 단계 자체는 여전히 필요했다 — 1단계의 부트스트랩 순환(설정 파일이 자기가
가리키는 디렉터리 안에 있을 수 없다)은 기본값을 옮기든 말든 성립한다.

### 4단계 — 라이브러리 백업 (기본값 변경을 대체)

**~~신규 설치의 기본값을 `<Documents>/PaleoBytes/Modan2` 로 바꾼다.~~ 철회
(2026-07-29).** 대신 배경이 지적한 진짜 문제 — 조사 7이 확인한 대로 **미디어에는
백업이 아예 없고 DB 백업은 같은 디스크에 있다** — 를 직접 친다.

명시적인 **"라이브러리 백업"** 동작을 준다. 결과물은 자족적 아카이브 하나이고,
사용자는 그것을 원하는 곳에 둔다 — 외장 드라이브든 OneDrive든. **ZIP은 동기화에
안전하다. 라이브 SQLite가 아닐 뿐이다.**

이 형태가 기본값 변경보다 나은 점:

- **되돌릴 수 있다.** 초안의 4단계는 이 계획에서 유일하게 되돌리기 어려운
  결정이었고, 그래서 OneDrive 실측이 선행 조건이었다. 백업 기능에는 그 선행
  조건이 없다 — **1·2단계를 막던 것이 사라진다.**
- **기존 사용자 처리가 필요 없다.** 아무도 이사하지 않으므로 안내 대화상자,
  "나중에/다시 묻지 않기" 상태, 옛 위치 폴백이 전부 불필요하다.
- **동기화 폴더에 두든 말든 안전하다.** 사용자가 자기 상황을 판단할 필요가 없다.

**구현 메모.** 현재 ZIP 패키지는 **데이터셋 단위** 다
(`MdUtils.create_zip_package(dataset_id, ...)`, 스키마 1.2). 라이브러리 전체를
감싸려면 순회 계층이 하나 필요하다 — 공짜는 아니지만 초안 4단계의 이전 UX +
기존 사용자 안내 + OneDrive 실측을 합친 것보다 작다. 복원 경로
(`import_dataset_from_zip`)가 이미 있다는 점도 유리하다.

**남는 것.** 기본값이 관례에 맞지 않는다는 사실 자체는 남는다. 개정 근거 1대로
그 값을 데이터 위험과 바꿀 이유가 없다고 본다. 판단이 바뀔 조건은 둘이다 —
조사 8대로 WAL을 켜게 되거나, OneDrive 실측이 충돌 사본 우려를 반증하는 경우.

## 위험

1. **부분 이전.** 가장 큰 위험. 2단계 알고리즘의 3·6·7번(백업 먼저, 검증 후 삭제,
   성공 후 경로 갱신)이 이걸 막는 장치다. 취소도 "이미 복사한 것을 되돌린다" 가
   아니라 "원본을 지우지 않는다" 로 안전을 확보한다.
2. **기본 인자 함정(조사 2).** 놓치면 설정을 바꿔도 일부 경로가 조용히 옛 곳을
   가리킨다. **갈라진 방향이 "읽기는 새 위치, 쓰기는 옛 위치" 이므로 첨부만
   확인하는 테스트는 정확히 이 버그를 놓친다** — 1단계 테스트 목록 참조.
3. **동기화 폴더의 용량·대역폭.** OneDrive/Dropbox가 Documents를 관리하면 수 GB의
   3D 모델이 동기화 대상이 된다. 이것이 **설정 가능화가 기본값 변경보다 먼저인 또
   하나의 이유** 다 — 곤란한 사용자는 옮길 수 있어야 한다.
4. **네트워크 드라이브의 SQLite.** 설정 가능해지면 누군가 DB를 네트워크 공유에
   둘 것이다. SQLite는 그런 환경에서 잠금이 불안정하다. 경고를 띄우거나 문서화가
   필요하다.

5. **동기화 폴더의 SQLite — 이 위험이 4단계를 철회시켰다.** ★ (2026-07-29 개정)

   위 4와 같은 계열인데 범위가 더 넓다. OneDrive/Dropbox 클라이언트가 쓰기 도중
   파일 핸들을 잡고 업로드하면 잠금 충돌이나 손상 위험이 있고, **두 머신에서 같은
   라이브러리를 열면 동기화 클라이언트는 병합하지 않고 충돌 사본을 만든다** —
   조용히 갈라진 라이브러리가 된다.

   초안은 이것을 "실측 후 결정" 으로 미루고, 필요하면 미디어는 Documents에 DB는
   로컬에 갈라 두는 절충을 제시했다. **그 절충은 두 순수 선택지보다 나쁘다** —
   DB 없는 `data/` 는 객체 id로 이름 붙은 파일 더미이고 랜드마크 좌표는 DB에만
   있으므로, Documents만 백업되면 복구 가치가 0이다. beta.2가 확보한 "한 폴더가
   곧 완전한 라이브러리" 를 깨뜨린다.

   그래서 갈라 두는 대신 **기본값을 옮기지 않고 백업을 만드는 쪽** 을 택했다
   (4단계). 이 위험은 이제 기본값에는 해당하지 않고, **사용자가 스스로 동기화
   폴더를 지정했을 때만** 남는다 — 위험 4와 함께 문서화 대상이다.

6. **Files On-Demand 는 "느림" 이 아니라 "간헐적 실패" 다.** ★

   초안은 이걸 "실사용 확인 필요" 로만 적었는데 성격을 잘못 잡았다. 핵심은
   `os.path.exists()` 가 **True 를 돌려주는데 실제로 열면 오프라인이라 실패할 수
   있다** 는 것이다. 수천 개 이미지를 순회하는 앱에서는 지연이 아니라 산발적인
   예외로 나타나고, 재현이 어렵다. 파일 존재 확인과 열기를 분리해 다루는
   코드(`has_archived_original` 등)가 특히 취약하다.

7. **설정된 경로가 사라졌을 때.** ★ (초안에 빠져 있던 케이스)

   이전 실패는 다뤘지만, 설정 가능해진 **뒤의 일상 케이스** 가 없었다 — 외장
   드라이브 미연결, 네트워크 공유 다운, 사용자가 폴더를 옮김, OneDrive가 위치를
   바꿈.

   그때 앱이 그 경로에 **조용히 빈 라이브러리를 새로 만들면 사용자에게는 데이터
   소실로 보인다.** 시작 시 명시적으로 알리고 멈춰야 한다: "설정된 데이터 위치를
   찾을 수 없습니다: <경로>. 드라이브가 연결되어 있는지 확인하거나 위치를 다시
   지정하십시오." 자동으로 기본값으로 되돌아가는 것도 같은 이유로 안 된다 — 빈
   라이브러리가 열리고 사용자는 데이터를 잃었다고 생각한다.

   **개정 후 이 위험의 비중이 올라간다.** 초안에서는 이것이 여러 안전장치 중
   하나였지만, 기본값을 옮기지 않기로 한 이상 **경로가 이상해지는 경우는 전부
   사용자가 직접 지정한 경우** 다. 즉 1단계에서 반드시 함께 구현해야 한다.

## 범위에서 제외

- **`temp/`** — 진짜 임시 파일이므로 OS 임시 위치가 맞다. 별건.
- **`--db` 플래그와의 관계.** DB만 따로 옮기는 기존 수단은 유지한다. 저장소 설정과
  독립적으로 동작해야 한다(현재도 그렇다).
- **여러 데이터 위치(라이브러리 전환).** 요구가 확인되지 않았다.

위험 7의 부재 경로 처리), 2단계는 자족적인 함수 하나에 테스트가 붙는다. 3단계는
끝났고, 4단계는 데이터셋 단위 ZIP 위에 순회 계층을 얹는 일이다.

**(2026-07-29)** 개정으로 전체 규모가 줄었다. 초안 4단계에 딸려 있던 이전 UX,
기존 사용자 안내 상태 기계, OneDrive 실측이 전부 사라졌다.

**미디어 경로가 계산된다는 조사 1의 발견이 이 작업을 "DB 마이그레이션" 에서
"디렉터리 이동" 으로 낮췄다.** 착수 전 이걸 확인하지 않았다면 훨씬 큰 일로
잡았을 것이다.
