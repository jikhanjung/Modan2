### 범위 정정 — 처음엔 첨부 파일만 설정 가능하게 했다

1단계를 "저장소(`data/`)만" 으로 좁혀 구현했다가 되돌렸다. 계획서 설계 표는
DB·미디어·백업을 **한 덩어리로** 설정 가능하게 하는 것이고 2단계 이전 기능도 셋을
함께 옮기는데, 좁힌 구현은 **UI 라벨이 "Data folder" 인데 실제로는 `data/` 만
옮기는** 상태를 만들었다. 라벨이 약속을 지키지 않는 쪽이 나쁘다.

## 왜 기본값을 옮기지 않기로 했나

P03 초안의 동기는 "OneDrive의 Known Folder Move가 프로필 루트를 백업하지 않아
연구 데이터의 유일한 사본이 백업에서 빠진다" 였다. 착수 전에 근거를 확인하다가
**계획서에 없던 사실 두 개** 가 나왔고, 그게 판단을 뒤집었다.

### 조사 7 — `backups/` 는 DB만, 같은 디스크에 백업한다

`MdModel.prepare_database()` (`:2679-2704`) 는 `Modan2.db` 를 날짜별로 복사해 10개를
유지한다. `data/` 의 이미지·3D 모델은 **대상이 아니고**, 사본은 원본과 같은
디스크에 있다.

즉 현재 백업 체계는 DB 손상에는 대비되지만 **디스크 손실에는 무력하고, 원본
미디어는 어느 쪽에도 대비가 없다.** beta.2가 확보했다고 여긴 "한 폴더 복사가 곧
완전한 백업" 은 사용자가 직접 복사할 때만 성립하고, 앱이 스스로 하는 일은
절반뿐이었다.

**배경이 지적한 피해는 위치 문제로 위장한 백업 문제였다.**

### 조사 8 — SQLite는 rollback journal 모드다

`gDatabase = SqliteDatabase(database_path, pragmas={"foreign_keys": 1})` — WAL이
아니다. 동기화 관점에서는 다행이다(WAL은 `-wal`/`-shm` 이 본체와 정합해야 해서
클라이언트가 다른 시점에 올리면 깨지는 게 보장된다). 다만 **위험을 줄일 뿐 없애지
않는다** — 충돌 사본 문제는 저널 모드와 무관하다. 나중에 성능 목적으로 WAL을 켜면
이 판단을 다시 봐야 한다.

### 결론

셋을 근거로 기본값을 유지하기로 했다.

1. **Zotero 선례.** 연구용 도구 + SQLite + 첨부 저장소라는 구조가 사실상 동일한데
   기본값이 `~/Zotero` — 프로필 루트다. 관례를 몰라서가 아니라 "`zotero.sqlite` 를
   동기화 폴더에 두지 말라" 를 공식 문서로 경고하면서 내린 선택이다.
2. **트레이드의 방향이 나쁘다.** 백업 안 됨은 드물게·시끄럽게 실패한다(디스크가
   죽고 즉시 안다). 동기화 폴더의 SQLite는 상시로·조용하게 실패한다 — 두 머신에서
   같은 라이브러리를 열면 OneDrive는 병합하지 않고 충돌 사본을 만들고, 사용자는
   한동안 모르며 알았을 때는 어느 쪽이 진짜인지 판단할 수 없다.
3. **분리안(미디어는 Documents, DB는 로컬)은 두 순수 선택지보다 나쁘다.** DB 없는
   `data/` 는 객체 id로 이름 붙은 파일 더미이고 랜드마크 좌표는 DB에만 있으므로
   복구 가치가 0이다.

대신 4단계를 **명시적 "라이브러리 백업"** 으로 바꿨다. **스냅샷은 동기화에
안전하고 라이브 SQLite는 아니다.** 부수 효과로 이 계획에서 유일하게 되돌리기
어려웠던 결정이 사라졌고, **1·2단계를 막고 있던 OneDrive 실측도 선행 조건이
아니게 됐다.**

## 1단계 구현

### 부팅 순서가 이 작업의 절반이었다 ★

DB는 **설정을 읽기 전에** 열리고 있었다 — `MdAppSetup.initialize()` 가
1. `_prepare_database` → 2. `_load_settings` 순서였다. 데이터 디렉터리가 설정인데
그 안에 있는 DB를 먼저 열면 설정은 도달할 수 없다. **순서를 뒤집는 것이 DB를
설정에 따르게 하는 전제**였고, `_load_settings` 는 DB를 건드리지 않으므로 안전하다.

새 순서와 각 단계의 이유:

1. `_load_settings` — 데이터 디렉터리는 설정이므로 그 안의 무엇도 열기 전에 읽는다.
2. `_apply_data_directory` — `mu.set_data_directory()`, 그리고 **`ensure_directories()`
   가 무언가를 만들기 전에** 부재 검사. 이 둘의 순서가 뒤집히면 뽑힌 외장 드라이브가
   조용한 빈 라이브러리가 된다.
3. `_prepare_database` — `--db` 가 있으면 그것이, 없으면 `mu.get_database_path()`.

**로그는 그보다도 먼저다.** `main.py:setup_logging` 이 `preferences.json` 을 직접
읽는다(`mu.read_configured_data_directory`). 이게 가능해진 것은 devlog 277이 설정을
데이터 디렉터리 **밖으로** 뺐기 때문이다 — 안에 있었을 때는 설정을 찾으려면 찾으려는
그 값을 이미 알아야 했다. **초안이 "로그는 부트스트랩 때문에 옮길 수 없다" 고 한
근거가 3단계로 사라졌다.**

### 로그도 함께 옮겼다 (계획서와 다른 결정)

계획서는 로그를 제외했고 근거가 둘이었다. 그런데 **둘 다 지금은 성립하지 않는다**:

- *부트스트랩* — 위 대로 사라졌다.
- *"조사할 때 로그가 데이터와 같은 폴더에 있어야 한 곳만 보면 된다"* — 데이터가
  옮겨가는데 로그가 남으면 **이 근거가 오히려 반대편을 가리킨다.**

그래서 로그도 데이터 디렉터리를 따라간다.

**다만 `setup_logging` 은 없는 디렉터리를 만들지 않는다.** 만들면 두 번 잘못된다 —
2단계의 부재 검사가 볼 증거를 없애고(뽑힌 드라이브가 빈 라이브러리로 보인다),
그 실패를 설명하는 로그가 아무도 찾을 수 없는 곳에 쓰인다. 이 상호작용은 구현 중에
실제로 밟았고(설정한 디렉터리를 지우고 실행했더니 경고가 안 떴다), 회귀 테스트를
붙였다.

### 핵심 — 기본 인자 함정 제거

`MdImage`/`MdThreeDModel` 의 `base_path=mu.DEFAULT_STORAGE_DIRECTORY` 는 **import
시점에 한 번 평가**되므로 설정을 반영할 수 없었다. 더 나쁜 건 갈라진 방향이다:
경로를 명시하던 쪽은 대체로 *읽기*(뷰어·컨트롤러)였고, 기본값에 묶인
`MdModel` 내부는 전부 *쓰기·삭제·복사* 였다. 설정을 켜는 순간 **읽기는 새 위치,
쓰기는 옛 위치** 가 될 뻔했다.

- `MdUtils.get_storage_directory()` — 유일한 해석 지점. `_get_storage_dir` 을
  승격시켜 경로 상수 옆으로 옮겼다.
- `MdModel._storage_base(base_path)` — `None` 센티넬을 실제 경로로 바꾼다.
- 기본값을 쓰던 5개 함수 전부 `base_path=None` 으로. `MdThreeDModel.add_file` 은
  **`base_path` 파라미터가 아예 없었다** — 추가했다.

### 함께 정리한 것

- **백업 경로의 같은 함정.** `prepare_database` 가 `mu.DB_BACKUP_DIRECTORY`(import
  시점 상수)를 쓰고 있어 위치를 바꿔도 백업은 옛 곳에 계속 쌓였을 것이다.
  `mu.get_backup_directory()` 로 호출 시점 해석으로 바꿨다.
- **죽은 UI 복구.** `preferences_dialog.select_folder` 는 `edtDataFolder` 를
  참조하는데 그 위젯을 만드는 곳이 없었다. 고른 폴더는 다이얼로그 인스턴스에만
  남고 사라졌다. 위젯(읽기 전용 경로 + Browse + Reset)을 만들고
  `preferences.json` 의 `data.directory` 에 저장한다.
- **`Modan2.py` 의 무조건 덮어쓰기 제거.** `read_settings` 가
  `m_app.storage_directory` 를 항상 기본값으로 덮어써서 설정이 도달할 수 없었다.
  이제 `mu.get_storage_directory()` 의 **거울**일 뿐이고 진실의 출처가 아니다 —
  devlog 272가 정확히 "출처가 둘" 때문에 데였다.
- **`migrate.py` 의 중복 DB 경로 정의 제거.** `MdModel.database_path` 를 가져온다.
  devlog 272에서 설정 경로가 두 곳에 정의돼 load/save가 어긋났던 것과 같은 구조였다.
- **`serialize_dataset_to_json` 의 `storage_dir` 파라미터 삭제.** 받아서
  `os.path.abspath(...)` 를 대입 없이 평가하고 버렸다. 내보내는 파일 참조는 전부
  패키지 루트 기준 상대 경로라 파라미터 자체가 무의미했다. ruff B018이 못 잡은
  이유는 표현식이 함수 호출이라 부작용 가능성을 가정하기 때문이다.

### 위험 7 — 설정된 경로가 사라졌을 때

**기본값을 옮기지 않기로 하면서 이 위험의 비중이 올라갔다** — 경로가 이상해지는
경우는 이제 전부 사용자가 직접 지정한 경우다. 그래서 1단계에 포함했다.

`MdUtils.describe_data_directory_problem()` + `MdAppSetup._apply_data_directory()`.
사용자 지정 경로만 검사하고(기본값은 요청 시 생성되므로 부재가 아무 의미도 없다),
문제가 있으면 경로를 이름으로 알리고 [종료] / [기본 위치 사용] / [그대로 시작] 을
묻는다. **조용히 진행하거나 자동으로 기본값으로 되돌아가는 것은 둘 다 금지** —
그 경로에 빈 라이브러리가 새로 생기고, 사용자에게는 데이터 소실로 보인다.

**처음엔 이 검사를 메인 창에 뒀는데 너무 늦었다.** 그때는 `ensure_directories()` 가
이미 디렉터리를 다시 만든 뒤라 검사가 항상 통과한다. 검사는 **아무것도 만들기 전,
DB를 열기 전** 이어야 하므로 `MdAppSetup` 으로 옮겼다. 대화상자는 `main.py` 가
콜백으로 넘긴다 — 콜백이 없으면(스크립트·테스트·`--self-test`) 경고만 남기고
진행한다. 물어볼 사람이 없는 곳에서 모달을 띄우면 CI가 실패가 아니라 멈춘다.

이 대화상자는 **의도적으로 번역하지 않았다.** `_load_translations` 보다 먼저 도는
지점이라 `tr()` 을 써도 영어가 나오고, 처리한 척만 하게 된다.

## 테스트

`tests/test_storage_directory.py` 신규 50건. 설계 원칙 하나가 이 파일 전체를
결정했다:

> **첨부가 지정한 곳에 생기는지만 확인하면 이 버그를 정확히 놓친다.**

갈라진 방향이 "읽기는 새 위치, 쓰기는 옛 위치" 였으므로, 모든 케이스가 **부정도
함께 단언한다** — `no_default_writes` 픽스처가 테스트 본문이 기본 디렉터리에 파일을
하나라도 만들면 실패시킨다. 덮은 동작: 첨부·조회·데이터셋 간 이동·이미지 교체·
이미지/3D 복제·아카이브된 원본·데이터셋 삭제·ZIP 내보내기·재시작 후 지속.

부팅 순서와 부재 경로도 덮었다: 설정이 DB보다 먼저 읽히는가, `--db` 가 여전히
이기는가, 없는 디렉터리가 **묻기 전에 만들어지지 않는가**, 종료가 DB를 열기 전에
멈추는가, `setup_logging` 이 그 디렉터리를 만들어 검사를 무력화하지 않는가.

`tests/dialogs/test_preferences_dialog.py` 에 데이터 폴더 UI 9건 추가.

### 픽스처가 버그를 재현하고 있었다 ★

직접 재바인딩하고 있었고, 주석에 이유까지 적혀 있었다. 그런데 **목록에 없던

드러났다. 이제 픽스처는 리졸버 하나만 패치한다.

`tests/test_image_attach_downscale.py` 의 `_redirect_storage` 도 같은 계열의
우회(메서드 통째로 교체)였고 함께 정리했다.

## 범위 밖으로 남긴 것

- **기존 파일은 옮기지 않는다.** 위치를 바꿀 때 "기존 파일은 그대로 남는다" 를
  명시적으로 알린다. 수 GB를 조용히 반쯤 복사하는 진행 표시줄보다 낫다. 이전은
  2단계다.
- **설정 변경은 다음 실행부터 적용된다.** DB가 이미 열린 뒤에야 설정을 바꿀 수
  있으므로, 절반만 적용하면(새 첨부는 여기, DB는 저기) 라이브러리가 둘로 쪼개진다.
  "다시 시작 필요" 를 알린다.
- **`--db` 는 데이터 디렉터리와 독립이다.** 파일을 직접 지정하는 수단이고 그대로
  우선한다.
- `MdObject.update_image` 의 `if img is None:` 분기는 `get_image()` 가 빈 경우
  `IndexError` 를 내므로 도달 불가능하다. 유일한 프로덕션 호출부가
  `has_image()` 로 감싸고 있어 실제 버그는 아니다. 건드리지 않았다.

## 부수 발견 — `pytest` 가 사용자의 실제 DB에서 테이블을 지운다 ★

이 작업과 무관한, **기존부터 있던 데이터 손실 위험**이다. 저장소 경로를 쫓다가
발견했다.

`tests/test_landmark_parsing.py` 등 **4개 파일의 픽스처가 `MdModel.gDatabase` 만
바꾸고 모델의 `_meta.database` 는 그대로 둔다.** peewee의 `create_tables`/
`drop_tables` 는 모델의 `_meta.database` 를 쓰므로, 임시 DB에 만드는 척하면서
**실제 `~/PaleoBytes/Modan2/Modan2.db` 에 테이블을 만들고 지운다.**

`_meta.database` 를 재바인딩하지 않는 파일:

- `tests/test_landmark_parsing.py`
- `tests/test_landmark_count_consistency.py`
- `tests/test_missing_sentinel_import.py`
- `tests/test_procrustes_missing.py`
- `tests/test_unimputable_landmarks.py`

**내 변경 이전 코드로 재현했다.** 작업 트리를 stash 하고 원본 상태에서
`pytest tests/test_landmark_parsing.py` 를 실행:

```
BEFORE: [mdanalysis, mddataset, mdimage, mdobject, mdthreedmodel, migratehistory]
        17 passed
AFTER:  [mdanalysis,            mdimage,           mdthreedmodel, migratehistory]
```

**17건이 통과하면서 사용자의 `mddataset`·`mdobject` 테이블이 사라진다.** 이 개발
환경의 DB는 모든 테이블이 0행이라 잃은 것은 없었고, 07-28 백업에도 같은 흔적이
남아 있어 이전부터 있던 문제임이 확인된다. 하지만 **실제 데이터를 가진 사람이
`pytest` 를 돌리면 데이터셋과 개체가 전부 지워진다.**

DB는 `backups/Modan2.db.20260729` 에서 복원했고(마이그레이션 9까지 정상), 내
테스트 수정 이전에 실제 `backups/` 로 흘러든 파일 두 개(`chosen.db.*`,
`test.db.*`)도 지웠다.

### 고쳤다

**1. 픽스처 5개.** `conftest` 에 `bound_database` 픽스처를 만들어 올바른 패턴을
한 곳에 모았다 — `gDatabase` 와 **모든 모델의 `_meta.database` 를 함께** 바꾸고,
테이블을 만들고, 끝나면 드롭한 뒤 원래 바인딩을 복원한다(테스트가 실패해도).
다섯 파일은 이제 세 줄이다:

```python
@pytest.fixture
def setup_database(bound_database):
    yield bound_database(test_db, [MdDataset, MdObject])
```

**2. 안전망.** 픽스처를 고치는 것만으로는 부족하다 — 실패가 조용하고 다시 넣기
쉽다. `conftest` 에 세션 스코프 autouse 픽스처를 넣어, **어떤 테스트가 돌기 전에
기본 바인딩을 임시 파일로 돌린다.** 이제 같은 실수를 해도 그 임시 파일이 망가진다.

망을 실제로 검증했다 — 옛 버그 패턴을 그대로 쓴 테스트 파일을 일부러 만들어
실행하니 모델이 `/tmp/pytest-of-.../session-db0/Modan2.db` 에 묶였고 실제 DB는
그대로였다.

**3. 회귀 테스트.** `TestTheRealDatabaseIsOutOfReach` 3건 — 기본 바인딩이 실제
경로가 아닌가, 모델 5개가 전부 그런가, 모델을 통한 쓰기가 실제 파일에 닿지
않는가(mtime 대조). 안전망을 지우면 이게 깨진다.

**검증**: 전체 스위트 실행 전후로 실제 DB가 **바이트 단위로 동일**하다(md5 대조).
이전에는 같은 실행이 테이블 두 개를 지웠다.
