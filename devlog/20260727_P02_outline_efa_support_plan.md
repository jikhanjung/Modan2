# 아웃라인 분석(타원 푸리에, EFA) 지원 구현 계획

## 날짜
2026-07-27

## 배경

[[20260722_237_semilandmark_support_plan]] 은 EFA를 **범위 밖**으로 결론지었다:

> **EFA 자체는 Modan2 범위 밖**이다 — 랜드마크가 아닌 푸리에 계수를 다루는 별개
> 패러다임이라 평행 서브시스템이 되므로, 별도 도구나 내보내기로 처리한다.

**이 결론을 뒤집는다.** 근거는 두 가지다.

### 1. 통계·탐색 층은 이미 의미 중립적이다

당시 판단은 "계수는 랜드마크가 아니다"에서 출발했는데, 코드를 보면 하류가 그
구분을 하지 않는다.

- `MdStatistics.PerformPCA` (`MdStatistics.py:208`) 는 `landmark_list` 를 그냥
  평탄화해 행렬을 만든다. 숫자가 무엇인지 모른다.
- 형상 복원인 `unrotate_shape` (`dialogs/data_exploration_dialog.py:2820`) 는
  `shape @ inv(R) + mean` — **순수 선형 연산**이라 역시 의미를 모른다.
- CVA/MANOVA 그룹화, 산점도, 범례, 회귀 오버레이, 점수 내보내기는 전부 점수만
  다룬다.

즉 **"정렬된 랜드마크 벡터"와 "EFA 계수 벡터"는 이 경계에서 실제로 동등하다.**
평행이 되는 것은 통계가 아니라 앞단(취득·변환)과 렌더 꼬리뿐이다.

### 2. EFA에는 정렬 단계가 아예 없다 — 파이프라인이 오히려 짧다

이건 앞선 논의에서 나온 지적이고, 계획을 크게 단순화한다. EFA의 정규화는
Procrustes와 성격이 다르다:

| | Procrustes | EFA 정규화 |
|---|---|---|
| 기준 | 평균 형상 (반복 갱신) | 없음 — 객체 자기 자신 |
| 방식 | 반복 수렴 | 닫힌 형태 해 (1차 하모닉 타원) |
| 상호 의존 | 표본들이 서로 영향 | 객체별 독립 |

위치는 DC 항(`A0`/`C0`, 윤곽 중심)을 버리면 자동으로 빠지고, 크기·회전·시작점은
1차 하모닉 타원에서 바로 나온다. **표본들을 서로 맞추는 단계가 없다.**

따라서 다음이 전부 불필요해진다: 수렴 처리, 기준 형상 관리, **분석용 작업
사본**(Procrustes가 결측 대치 때문에 원본을 보존하려고 유지하는 구조), 결측
랜드마크 대치(윤곽은 연속 추적선이라 개념 자체가 없다).

```
랜드마크:  추적 → MdDatasetOps → 반복 정렬 → 대치 → 벡터 → PCA/CVA/MANOVA
윤곽:      추적 → EFA 변환(객체별, 1패스)           → 벡터 → PCA/CVA/MANOVA
                                                      ↑ 여기부터 완전히 동일
```

### 적용 범위 메모 (237의 분류를 갱신)

237은 형태를 세 갈래로 나눴다: ① 매개변수 모델이 있는 규칙적 형태(Raup 감김 등)
→ 이론 형태학, ② 모델화하기 어려운 상동 곡선 → 세미랜드마크, ③ 닫힌 윤곽 → EFA.

이 계획은 ③을 Modan2 안으로 들인다. **랜드마크 → 준랜드마크(곡선) → 윤곽** 은
"상동점을 몇 개나 특정할 수 있는가"가 줄어드는 자연스러운 연속선이고, 마지막
칸만 외부 도구로 보내는 것은 사용자에게 인위적인 단절이다.

## 현재 코드 구조 (조사 결과)

### 이미 깔려 있는 발판

준랜드마크 작업이 EFA에 필요한 것을 대부분 만들어 놨다.

| 필요한 것 | 이미 있는 것 |
|---|---|
| 윤곽 추적 UI | Curve 모드 + 라이브와이어 스냅 (devlog 240) |
| 원시 윤곽 저장 | `MdObject.curve_raw_json` (`MdModel.py:482`) |
| 데이터셋 수준 파라미터 | `MdDataset.curve_config_json` (`MdModel.py:235`) |
| 폴리라인 렌더링 | 곡선 표시 (`show_curve` 체크박스) |
| 분석 파라미터 UI 슬롯 | `comboSuperimposition` (`dialogs/analysis_dialog.py:73`) |

`get_curve_config()` 는 이미 **곡선별로 `{이름, 목표 점 개수, 리샘플 방식,
시작 인덱스}`** 를 담는 리스트다. **하모닉 개수는 "곡선당 준랜드마크 개수 `N`"과
정확히 같은 성격의 데이터셋 수준 파라미터**이므로 이 구조를 그대로 확장한다.

### 분기 지점

정렬은 `ModanController._prepare_landmarks(superimposition_method)`
(`ModanController.py:1085`) 안에서 `ds_ops.procrustes_superimposition()`
(`:1143`) 로 수행되고, 결과를 `landmarks_data` 로 평탄화해 돌려준다
(`:1149`). **윤곽 데이터셋은 이 함수에서 분기해 EFA 경로를 타고, 같은 모양의
벡터 리스트를 반환하면 된다.** 그 아래(`run_analysis:810` 이후)는 무변경.

### 분석 결과 저장

`MdAnalysis` (`MdModel.py:2521`) 에는 이미 필요한 필드가 있다:
`superimposed_landmark_json`(형상 복원의 평균 계산에 쓰임),
`pca_rotation_matrix_json`, `pca_analysis_result_json` 등. **계수 벡터를
`superimposed_landmark_json` 에 그대로 넣으면 `unrotate_shape` 가 수정 없이
동작한다** — 이름이 landmark일 뿐 내용은 "정규화된 형상 벡터"다.

이름과 내용이 어긋나는 것이 마음에 걸리면 필드를 추가하는 대신 **주석으로
의미를 확장**하는 편이 낫다. 새 필드는 마이그레이션·직렬화·ZIP 패키지 스키마까지
파급된다.

## 데이터 모델 설계

### 데이터셋 모드 (신규)

`MdDataset` 에 `object_type` 을 추가한다(기본 `"landmark"`, 신규 `"outline"`).
`dimension` 과 같은 성격의 데이터셋 수준 불변 속성이다.

**혼용은 금지한다.** 랜드마크 객체와 윤곽 객체가 한 데이터셋에 섞이면 벡터가
비교 불가능하다. 데이터셋 생성 시 정하고 이후 변경 불가(또는 비어 있을 때만
변경 가능).

### 닫힌 곡선 플래그

현재 곡선은 **열린 추적선**이다. EFA는 닫힌 윤곽을 요구하므로
`curve_config_json` 항목에 `"closed": true` 를 추가한다. 기존 항목에 키가 없으면
`false` 로 해석 — **하위 호환이 자동으로 성립**한다(237이 스키마 1.1→1.2에서 쓴
것과 같은 방식).

윤곽 데이터셋에서는 곡선이 정확히 하나이고 `closed`가 참이어야 한다.

### 하모닉 개수

`curve_config_json` 항목에 `"harmonics": <int>`(기본 20 정도). 준랜드마크의
`N` 과 같은 자리·같은 UI 패턴.

### 마이그레이션

`migrations/010_*.py` 로 `object_type` 컬럼 추가. `curve_config_json` 은 JSON
블롭이라 스키마 변경이 없다(키 추가만).

## 정규화 옵션 — 유일하게 진짜 결정이 필요한 부분

분석 대화상자의 `comboSuperimposition` 슬롯을 **데이터셋 모드에 따라 항목만
바꿔** 재사용한다.

| 데이터셋 모드 | 콤보 라벨 | 항목 |
|---|---|---|
| landmark | 중첩정렬방식 | 프로크루스테스 / 북스틴 / 강건적합 |
| outline | 정규화 | 없음 / 크기만 / 크기+회전+시작점 |

- **크기+회전+시작점** (표준). Kuhl & Giardina 방식으로 1차 하모닉 타원에서
  산출. 시작점 민감도 문제가 알려져 있으므로 기본값으로 두되 유일한 선택지로
  만들지 않는다.
- **크기만.** 방향이 생물학적으로 의미 있는 경우(촬영 방향이 일정한 표본, 좌우
  구분이 중요한 경우) 회전을 정규화하면 안 된다.
- **없음.** 이미 정규화된 좌표를 넣는 경우.

`MdAnalysis.superimposition_method` 필드에 그대로 저장한다(값 집합만 늘어난다).

### 계수 스케일에 대한 주의

프로크루스테스 좌표는 성분이 동질적이지만 **푸리에 계수는 하모닉마다 진폭
스케일이 다르다**. 고차 하모닉이 작아 PCA가 저차(= 큰 형태)에 지배되는데, 대개
바람직하지만 **"그냥 벡터"라는 등식이 정확하지 않은 유일한 지점**이다.
1단계에서는 표준화하지 않고(관행), 필요해지면 옵션으로 추가한다. **이 결정은
문서에 명시해야 한다** — 사용자가 결과를 해석할 때 알아야 하는 사실이다.

## 구현 단계 (권장 순서)

### 1단계 — EFA 변환 모듈 (UI 무변경, 순수 함수)

`MdOutline.py` 신설:

- `efa_coefficients(points, harmonics) -> np.ndarray` — 닫힌 폴리라인 → `(4H,)`
  계수 벡터 (2D 기준 하모닉당 a,b,c,d)
- `normalize_coefficients(coeffs, mode) -> np.ndarray`
- `synthesize_outline(coeffs, n_points) -> list[list[float]]` — 역합성

**테스트가 이 단계의 핵심이다.** 원 → 계수 → 역합성 → 원 왕복, 알려진 도형의
계수 검증, 회전·크기를 바꾼 같은 도형이 정규화 후 같은 계수를 내는지. `MdOutline`
은 순수 수치 모듈이라 `MdStatistics` 처럼 커버리지를 높게 유지할 수 있다.

### 2단계 — 데이터 모델 + 분석 경로 분기

- `MdDataset.object_type` + 마이그레이션 010
- `curve_config_json` 에 `closed`, `harmonics`
- `_prepare_landmarks` 에서 분기: 윤곽이면 각 객체의 `curve_raw_json` →
  `efa_coefficients` → `normalize_coefficients` → 벡터 리스트 반환
- 분석 대화상자 콤보 항목을 모드에 따라 교체

이 단계가 끝나면 **PCA/CVA/MANOVA와 산점도가 이미 동작한다** — 하류가 무변경이므로.

### 3단계 — 형상 복원 렌더링

`shape_to_object()` 와 뷰어 경로를 모드로 분기: 계수 벡터 → `synthesize_outline`
→ 폴리라인 → 기존 곡선 렌더러로 그리기.

여기서 "형상 격자(Shape grid)"와 형상 비교가 윤곽에서도 동작하게 된다. 와이어
프레임·베이스라인·폴리곤·랜드마크 인덱스 표시는 윤곽 모드에서 숨긴다.

### 4단계 (선택) — 임포트/익스포트

- **내보내기**: 계수를 CSV로. 윤곽 자체는 TPS `CURVES=` 로 이미 나간다.
- **가져오기**: 외부 윤곽 좌표(예: `.txt` 체인코드, Momocs `Out` 내보내기).
  1~3단계와 독립이므로 나중에 붙여도 된다.

## 구현 범위에서 제외 (기록 보존)

- **3D 윤곽 / 구면 조화 함수(SPHARM).** 2D 윤곽과 수학이 다르고 취득 방식도
  다르다. 3D 곡선 추적조차 아직 없다(TODOs 참조).
- **계수 표준화 옵션.** 위 "계수 스케일" 참조 — 필요성이 확인되기 전에는 넣지
  않는다.
- **다른 윤곽 방법**(반경 푸리에, 접선각 푸리에, 웨이블릿). EFA가 닫힌 윤곽의
  사실상 표준이고, 하나로 시작해 필요하면 정규화 콤보처럼 확장한다.

## 위험 요소

1. **`superimposed_landmark_json` 의 의미 확장.** 필드명이 내용과 어긋난다.
   새 필드를 만들면 ZIP 패키지 스키마(1.2 → 1.3)와 마이그레이션까지 번지므로
   주석으로 처리하는 쪽을 권하지만, 나중에 읽는 사람이 헷갈릴 여지가 있다.
   **결정 시 이유를 코드 주석에 남길 것.**
2. **시작점 민감도.** 1차 하모닉 정규화의 알려진 약점. "크기만" 옵션이 도피처가
   되지만, 문서에 한계를 적어야 한다.
3. **윤곽 추적 품질.** 라이브와이어는 열린 곡선용으로 만들어졌다. 닫힌 윤곽에서
   시작점과 끝점을 잇는 처리가 필요하고, 실제 표본 사진에서의 품질은 아직
   검증되지 않았다(TODOs의 미완 항목).
4. **혼용 금지의 강제 시점.** `object_type` 을 나중에 바꾸면 기존 분석 결과가
   무의미해진다. 데이터가 있으면 잠그는 규칙이 필요하다.

## 요약

237의 "범위 밖" 판단은 **통계·탐색 층이 이미 얼마나 의미 중립적인지를 과소평가**
한 것이다. 실제로 평행이 되는 것은 앞단 변환과 렌더 꼬리뿐이고, 그 사이는 전부
공유된다. 게다가 EFA에 정렬 단계가 없다는 점 때문에 파이프라인이 랜드마크 쪽보다
**짧다**.

새로 필요한 것은 모듈 3~4개다: EFA 변환, 데이터 모델 확장 + 분기 하나, 역합성
렌더 경로, (선택) 임포트/익스포트. **중첩정렬 3종 구현(devlog 250–254)보다 작은
작업**으로 보인다 — 그건 반복 알고리즘 셋을 수치적으로 맞춰야 했지만, 이건 결정적
변환 하나에 정규화 옵션이 붙는 형태다.

착수 여부는 3D 준랜드마크 곡선 추적, 슬라이딩 준랜드마크 등 다른 큰 항목과의
우선순위 문제다.

## 버전 (2026-08-13 결정)

**EFA가 들어가는 릴리스는 `0.3.0` 이다.** 1.0.0이 아니다.

순수 추가이므로(새 데이터 타입 + 새 분석, 기존 동작 제거 없음) semver상 minor가
맞다. 1.0.0을 쓰지 않는 이유는 크기가 아니라 **1.0이 기능에 대한 보상이 아니라
안정성에 대한 약속** 이기 때문이다. 가장 큰 새 서브시스템을 넣는 릴리스는 그
약속을 하기에 가장 나쁜 시점이다 — 새 패러다임이 트리에서 가장 덜 검증된 코드다.

1.0.0을 벌기 위해 남은 것:

- **포맷 고정.** 패키지 스키마가 릴리스마다 움직이는 중이고(1.3, 위험 1대로 EFA는
  1.4를 부른다), 1.0은 "이 포맷을 깨지 않는다" 는 뜻이다.

수도 있다. 사용자의 디스크에 이미 쓰인 필드의 **의미** 는 그렇지 않다. EFA 착수
직전에 굳혀야 할 것과 열어 둬야 할 것의 구분이 여기다.
