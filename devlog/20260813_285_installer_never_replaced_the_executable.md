# 설치 관리자가 exe를 한 번도 교체하지 않았다

## 날짜
2026-08-13

## 증상

beta.2가 설치된 머신에 beta.3을 설치했다. **설치는 성공했고**, 실행하면
스플래시도 창 제목도 **0.2.0-beta.2** 였다.

devlog 284에서 설치 관리자의 런타임 동작 세 가지를 확인하고 닫은 직후에 나왔다.
그 세 가지는 전부 **구버전 감지 프롬프트**에 관한 것이었고, 프롬프트는 정상이었다.
검증 항목이 실제 사용자 경로를 다 덮지 못했다는 뜻이다 — "묻는가" 는 확인했는데
"바뀌는가" 는 아무도 확인하지 않았다.

## 원인 — 두 결함이 겹쳐야 일어난다

### 1. 모든 릴리스의 exe가 `0.0.0.0` 으로 찍혔다

`build.py:prepare_version_info_file` 은 `build/file_version_info.txt` 를 템플릿으로
읽고, 없으면 폴백 문자열을 썼다. 그 폴백은 이렇게 생겼다:

```python
"    filevers=(0, 0, 0, 0),\n"
"        StringStruct('FileVersion', '0.0.0.0'),\n"
```

**플레이스홀더가 하나도 없다.** 그런데 바로 아래에서 `{{VERSION_TUPLE}}`,
`{{FILE_VERSION}}` 을 `.replace()` 하고 있었다. 코드는 치환하는 것처럼 보이고,
실제로는 아무것도 치환하지 않는다.

그리고 **`build/file_version_info.txt` 는 저장소에 존재한 적이 없다.**
`git log --all -- build/file_version_info.txt` 가 비어 있고, `.gitignore` 에
`build/` 가 있다. 즉 CI 러너에는 그 파일이 절대 없고, **모든 CI 빌드가 폴백을
탔다.**

옛 코드를 그대로 떼어 내 돌려 확인했다:

```
OLD CODE, beta.3 stamped: filevers=(0, 0, 0, 0)
OLD CODE, beta.2 stamped: filevers=(0, 0, 0, 0)
identical payload: True
```

버전 리소스가 **바이트 단위로 같다.**

곁가지로 `version_tuple` 자체에도 버그가 있었다. 전체 문자열에서 숫자만 긁어
모으므로 `0.2.0-alpha.2` 와 `0.2.0-beta.2` 가 **둘 다 `(0,2,0,2)`** 가 된다.
폴백 때문에 한 번도 도달하지 못한 코드였을 뿐이다.

### 2. `[Files]` 에 `ignoreversion` 이 없었다

```
Source: "...\Modan2\Modan2.exe"; DestDir: "{app}"
Source: "...\Modan2\*"; DestDir: "{app}"; Flags: recursesubdirs createallsubdirs
```

플래그가 없으면 Inno는 **파일마다 버전 리소스를 비교해 교체 여부를 스스로
정한다.** 기존 파일이 더 낮지 않으면 건너뛴다. 두 빌드가 똑같이 `0.0.0.0` 이므로
`Modan2.exe` 는 **항상 "이미 최신"** 이었다.

### 겹치면

설치 관리자는 파일을 건너뛰고도 **성공으로 끝난다.** 사용자에게는 설치가 정상으로
보이고, 실행하면 옛 빌드가 뜬다. **beta.3에만 있는 문제가 아니라 지금까지의 모든
업그레이드가 그랬다.** beta.2 이전에는 AppId가 없어 설치가 나란히 이루어졌기 때문에
증상이 다르게(중복 설치로) 나타났고, AppId를 고정한 beta.2부터 제자리 업그레이드가
되면서 이 형태로 드러났다.

## 고친 것

**둘 다 고쳤다. 하나만으로도 증상은 사라지지만, 각각이 조용히 실패했던 것이
이번 대가의 원인이다.**

1. **버전 리소스를 실제 값으로 찍는다.** 템플릿 파일 의존을 없애고 직접 생성한다.
   없는 파일을 견디는 폴백이 있었기 때문에 아무도 알아채지 못했으므로, **견딜
   대상 자체를 없앴다.**
2. **4번째 자리에 빌드 번호를 넣는다.** Windows 파일 버전은 숫자 네 개뿐이라
   `-alpha`/`-beta` 를 표현할 방법이 없다. 빌드 번호는 커밋 수라 릴리스 사이에도,
   한 릴리스의 프리릴리스 사이에도 단조 증가한다 — Inno가 요구하는 순서가 정확히
   그것이다.
3. **페이로드에 `ignoreversion`.** 우리 페이로드는 매 설치마다 통째로 교체된다.
   이전 버전 파일을 남기고 싶은 경우가 없다. 버전 숫자가 맞는지에 교체를 의존시키면
   같은 침묵이 실수 하나 거리에 남는다.
4. **`--version-file` 준비 실패를 삼키지 않는다.** `except Exception: print(warning)`
   이었다. 버전을 못 찍는 빌드는 **빨간 잡 하나로 죽는 편이**, 모든 사용자 머신에서
   업그레이드를 거부하는 설치 관리자를 내보내는 것보다 낫다.

`build.py` 는 스크립트라 import 하면 빌드가 돈다. 그래서 두 함수를
**`build_version_info.py` 로 분리**했다 — 테스트가 없었던 이유가 그것이었고,
테스트가 없었기 때문에 이 코드가 존재하는 내내 `0.0.0.0` 을 찍을 수 있었다.

## 왜 기존 테스트가 못 잡았나

`tests/test_version_consistency.py` 는 **버전이 여러 파일에 일관되게 나타나는지**를
검사한다. R06의 실패(문서 `conf.py` 가 `0.1.5` 에 멈춰 있던 것)를 겨냥한 것이다.

**이번 결함은 그 그물을 정의상 통과한다. 불일치가 없었기 때문이다** — 모든 것이
고르게 `0.0.0.0` 이었다. 일관성 검사는 "값이 서로 같은가" 를 묻지 "값이 옳은가" 를
묻지 않는다.

새 테스트는 후자를 묻는다: 0이 아닐 것, 프리릴리스 사이에 증가할 것,
alpha.2와 beta.2가 충돌하지 않을 것, 생성된 파일에 `{{` 가 남지 않을 것, 그리고
**페이로드 각 줄에 `ignoreversion` 이 있을 것.**

마지막 항목은 코드가 아니라 설치 스크립트를 검사한다. 이 결함의 절반이 거기
있었으므로, 거기도 그물이 필요하다.

## 검증됨 (2026-08-13, 0.2.0-beta.4)

**beta.4를 설치하고 실행하니 beta.4가 떴다.** 이 문장이 이 수정의 전체 검증이다 —
beta.3까지는 같은 절차가 옛 버전을 띄웠다.

부수적으로 **다른 드라이브 이전(devlog 286)도 함께 확인됐다.** 환경설정 창의 데이터
폴더가 `D:\Modan2` 로 잡혀 있었다. 즉 beta.4 하나가 Windows 전용 결함 두 개를
동시에 닫았다.

빌드 885, 자산 3종 + 체크섬, prerelease.

## 남는 것

~~**이 수정은 다음 릴리스가 나가야 검증된다.**~~ 위에서 닫혔다. 남는 교훈은
검증 절차 쪽이다 — Inno의 동작은 Windows에서만 확인되고, 그것이 devlog 274 이래
이 영역이 반복해서 미검증으로 남은 이유다.

검증 절차도 이번에 명확해졌다. "설치 관리자가 오류 없이 끝나는가" 가 아니라
**"설치 후 실행했을 때 새 버전 번호가 보이는가"** 다. 전자는 이 결함이 있는
빌드에서도 통과한다.

`ignoreversion` 은 **이미 설치된 빌드의 버전 리소스와 무관하게** 강제 교체하므로,
다음 릴리스는 `0.0.0.0` 이 박힌 기존 설치 위에도 정상적으로 덮인다. 사용자가 손으로
지우고 다시 설치할 필요는 없다.
