# 라이브러리 백업 (P03 4단계) — 그리고 백업은 손실이 없어야 한다

## 날짜
2026-08-08

## 한 일

1. **P03 4단계 — 라이브러리 백업/복원.** `Data ▸ Back Up Library` / `Restore
   from Backup`. 라이브러리 전체가 자족적 ZIP 하나가 된다.
2. **패키지 스키마 1.2 → 1.3: 분석 결과(`MdAnalysis`)를 담는다.** 백업만 켜고
   내보내기는 끈다.
3. 매뉴얼 FAQ의 백업 항목을 다시 썼다. "데이터 폴더를 손으로 복사하세요" 가
   아니라 실제 기능이 되었다.

## 형식 — 이미 있는 것을 감싼다

계획서대로 **데이터셋별 ZIP 패키지 위에 순회 계층 하나**다.

```
Modan2-library-20260808.zip   (ZIP_STORED)
├── library.json
└── datasets/
    ├── 0001_Trilobites.zip   (기존 내보내기 패키지와 같은 형식)
    └── 0002_Ammonites.zip
```

**쓰는 쪽과 읽는 쪽 모두 이미 검증된 코드**(`create_zip_package` /
`import_dataset_from_zip`)를 그대로 쓴다. 복원 못 하는 백업은 백업이 아니고,
복원 경로를 새로 쓰면 그게 정확히 아무도 안 써 본 코드가 된다.

바깥 아카이브는 `ZIP_STORED` 다. 멤버가 전부 이미 deflate 된 ZIP이라 다시
압축하는 것은 시간만 쓴다.

## 두 가지 불변식

**1. 완전하거나, 파일이 없거나.** 임시 이름(`.partial`)으로 조립하고 마지막에
`os.replace` 한다. 중단된 실행은 잘린 파일 대신 아무것도 남기지 않는다. **없는
백업보다 나쁜 것이 있다고 믿는 백업이다.** 2단계 이전 기능의 불변식과 같은
성격이고, 같은 이유다.

**2. 복원은 더하기다.** 기존 라이브러리를 지우지 않고 옆에 추가하며, 이름이
겹치면 `_unique_dataset_name` 이 새 이름을 준다. 그래서 **실수로 복원해도 아무것도
파괴할 수 없다.** "먼저 비우고 복원" 이었다면 잘못 누른 복원이 되돌리려던 바로 그
손실을 일으킨다. 대화상자가 어느 쪽인지 명시한다 — "restore" 는 보통 반대를
뜻하기 때문이다.

## 빠진 파일을 보고한다 — `create_zip_package` 는 삼킨다

`create_zip_package` 는 미디어 복사에 실패하면 **경고 로그만 남기고 계속한다**
(`logger.warning(f"Failed to include file {src}")`). 내보내기에서는 변호 가능하지만
**백업에서는 안 된다** — 구멍 난 안전망이 멀쩡한 척한다.

그래서 쓴 사람을 믿지 않고 **쓰인 아카이브를 검증한다**: 데이터셋 JSON에서 기대
경로를 만들어 ZIP의 `namelist()` 와 대조하고, 없는 것을 결과에 담아 UI가 보고한다.
2단계에서 복사본을 검증한 것과 같은 발상이다.

## 분석 결과 — 처음엔 뺐다가 넣었다

**처음 구현은 분석을 제외했다.** 근거는 "분석은 랜드마크에서 파생되고 랜드마크는
백업에 있으니 복구 불가능한 손실이 아니다" 였고, 계획서의 4단계 범위("순회 계층
하나")에도 맞았다.

**사용자 지적으로 뒤집었다: "백업이면 analysis 들어가는 게 맞을 것 같은데."**
맞다. **"다시 계산할 수 있다" 는 "그때 돌린 그 분석을 아직 가지고 있다" 와 다르다.**
분석은 날짜가 찍힌 작업 기록이고, 논문에 들어간 그 실행이다. 백업이 손실을
허용하면 그 순간 백업이 아니라 부분 내보내기다.

구현이 싼 것도 확인했다. `MdAnalysis` 는 **완전히 평평하다** — 결과가 전부 이미
JSON 문자열 컬럼이라 필드 복사가 곧 직렬화다. 중첩 관계는 `dataset` FK 하나뿐이고
복원 때 다시 걸면 된다.

**필드를 반영(reflection)하지 않고 `ANALYSIS_FIELDS` 로 나열했다.** 컬럼이 늘어날
때 "이것이 백업에 들어가야 하는가" 가 조용히 결정되지 않게 하려는 것이고, 새
버전이 쓴 패키지를 옛 버전이 계속 읽을 수 있게 하려는 것이기도 하다.

`created_at`/`modified_at` 도 함께 옮긴다. 오늘 날짜로 복원하면 **언제 한 작업인지를
왜곡한다.**

### 내보내기는 왜 그대로 두는가

`include_analyses` 는 **백업만 True, 내보내기는 False** 다. 분석 하나가
`raw_landmark_json` + `superimposed_landmark_json` 으로 **모든 객체의 랜드마크를 두
벌 더** 들고 있어서, 데이터셋 하나를 동료에게 건네는 것이 목적인 패키지의 크기를
몇 배로 만든다. 목적이 다르면 답이 다르다.

부수 효과로 `estimate_package_size`(내보내기 대화상자가 보여 주는 예상 크기)도
그대로 맞다. 내보내기에 분석을 켰다면 이 추정이 조용히 과소평가가 됐을 것이다.

스키마는 1.3으로 올렸지만 `analyses` 키는 **선택적** 이다. 1.2 이하 패키지와 모든
내보내기에는 없고, `validate_json_schema` 도 요구하지 않는다. 옛 버전이 1.3
패키지를 읽으면 분석만 빠진 채 정상 임포트된다.

## 남는 것 — 설정은 안 담는다

창 배치, 색, 언어. 애플리케이션이 다시 만들고 잃어도 클릭 몇 번이다. 매니페스트의
`includes`/`excludes` 에 **문장으로** 적었다 — 대화상자를 본 적 없는 사람이 몇 년 뒤
아카이브만 열어도 경계를 알 수 있어야 한다.

## 테스트

`tests/test_library_backup.py` 24개. 전체 **2019 passed**, 10 skipped.

무게가 실린 곳은 "파일이 도착했다" 가 아니라:

- 실패 시 `.partial` 조차 안 남는가
- 취소 시 파일이 없는가
- 디스크가 잃은 미디어가 **보고되는가**
- 복원이 기존 데이터셋을 **건드리지 않는가**, 이름 충돌이 새 이름을 받는가
- 데이터셋 하나가 깨져도 나머지가 들어오는가 (임포트마다 별도 트랜잭션)
- 분석의 `created_at` 이 보존되는가
- **내보내기에는 여전히 분석이 없는가** (기본값이 뒤집히면 잡힌다)
- 1.3 이전 패키지(=`analyses` 키 없음)가 여전히 임포트되는가

데이터셋 이름은 사용자 텍스트인데 그대로 ZIP 멤버 이름이 되므로,
`bad/name: "with" <chars>` 로 아카이브가 깨지지 않고 원래 이름은 매니페스트에
남는 것도 확인한다.
