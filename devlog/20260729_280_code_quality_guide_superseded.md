# `CODE_QUALITY_GUIDE.md` 을 공유 묶음에 넘기고 얼리기 — 279가 열어 둔 항목을 닫음

## 날짜
2026-07-29

## 배경

devlog 279가 `.guides/` 로 공유 가이드를 참조하기로 하면서 한 가지를 **미해결로
남겼다**: `docs/CODE_QUALITY_GUIDE.md` 는 이 프로젝트가 썼고
`.guides/desktop/code-quality.md` 는 그것을 증류한 것인데, 둘 중 무엇이 정본인가.

당시 옮기지 못한 이유는 CTHarvester였다. 그쪽 `TODOs.md` 의 품질 상태표가 이
문서의 **Appendix A 체크리스트**를 기준으로 채점하는데 공유본(7절)에는 그
체크리스트가 없어서, 기준을 옮기면 추적이 깨졌다.

**그 제약이 해소됐다.** CTHarvester devlog 120이 기준선을 자기 저장소 안으로
원문 복사해 얼렸고, "살아 있는 상호 의존은 이제 없음" 을 명시했다.

## 감사 — 공유본이 증류가 아니라 대체였다

옮기기 전에 "공유본에 없는데 잃으면 안 되는 것" 이 있는지 전수 확인했다.
절 수만 보면 14 → 7이라 축약처럼 보이지만, **공유 묶음은 파일이 여럿이고 내용은
흩어졌을 뿐 줄지 않았다.**

| 이 문서 | 옮겨간 곳 |
|---|---|
| §0 데스크탑이 왜 다른가 | `desktop/README.md` |
| §1–2 린트·타입 · §3–4 테스트 · §8 견고성 · §9 자원 · §10 i18n · §11 성능 · §13 죽은 코드 | `desktop/code-quality.md` |
| §5 크로스플랫폼 CI · §6 의존성 · §12 보안 스캔 · §14 게이팅 | `desktop/ci.md` |
| §7 패키징·릴리스 검증 | `desktop/packaging-release.md` |
| Appendix A 채택 체크리스트 | `desktop/README.md` |

위험해 보이던 네 항목(자원·메모리, i18n·인코딩, 성능, 개발 워크플로)을 키워드로
전수 조회했고 **전부 공유 묶음 안에 있었다.**

**규모가 결정적이었다** — 이 문서 2,609 단어, 공유 묶음 13,334 단어. 5배다.
깊이도 확인했다. 예를 들어 Qt 위젯 수명 항목에서 이 문서는 "~800 MB RSS 증가를
겪었다" 로 사례만 적는데, 공유본은 **처방까지** 적는다:
`sendPostedEvents(None, QEvent.DeferredDelete)` + `processEvents()` ×3 +
`gc.collect(0)`, 그리고 전체 `gc.collect()` 는 스위트 시간을 두 배로 만들었다는
것까지.

즉 공유본은 이 문서의 요약본이 아니라 **넘어선 판본**이다. 정본은 공유본이다.

## 그런데 지우지 않았다

**이 문서는 다른 기록들이 기준으로 삼는 날짜 박힌 기준선이고, 변하는 기준선은
아무것도 재지 못한다.** 인용하는 곳이 셋이다:

- **CTHarvester devlog 120** — 채택 상태표를 *이 판본의* Appendix A로 채점한다.
- **CTHarvester devlog 100·103** — 상대경로로 이 파일을 가리킨다. 그쪽이
  의도적으로 남긴 것이다: *그때 무엇을 보고 감사했는가* 의 기록이라서.
- **이 저장소 devlog 242** — `§6` 을 **번호로** 인용한다.

지우면 셋 다 조용히 무효가 된다. 그래서 **문서 맨 앞에 superseded 표시 + 절
이동 지도 + "고치지 말 것" 과 그 이유**를 넣었다. CTHarvester devlog 120의
"갱신되지 않는 것이 결함이 아니라 요건" 과 같은 논리다.

### 절 번호 함정 ★

CTHarvester가 발견한 것을 그대로 물려받는다. **번호는 이사를 견디지 못한다** —
이 문서 §7은 *Packaging & release verification*, 공유본 §7은 *Dead code,
complexity & duplication* 이다. 링크를 조용히 바꿔 달았다면 **링크는 멀쩡한 채 뜻만
틀렸을 것이다.** 그래서 문서 이름으로 인용하고 "가이드 §7" 로는 절대 쓰지 않는다.

## `docs/` 전체의 경계선

"관련 가이드를 전부 obsolete 시키는가" 를 확인하다 나온 결론인데, **겹치는 것은
이 문서 하나뿐이다.**

| 파일 | 판단 |
|---|---|
| `CODE_QUALITY_GUIDE.md` | 유일하게 *재사용 가능한 일반 가이드*로 쓰였다("principles transfer to any desktop stack"). 공유 묶음이 맡은 역할과 정확히 겹친다 → 넘김 |
| `BUILD_GUIDE.md` | *Modan2를* 어떻게 빌드하는가. `packaging-release.md` 는 원칙, 이건 절차 → 유지 |
| `TEST_RELEASE_PLAN.md` | 이 프로젝트의 릴리스 검증 계획 → 유지 |
| `GITHUB_PAGES_SETUP.md` | *이* 사이트가 어떻게 설정돼 있는가 → 유지 |
| `SCREENSHOT_GUIDE.md`·`architecture.md`·`performance.md` | 전부 이 저장소 고유 → 유지 |

그래서 규칙을 `docs/README.md` 와 `CLAUDE.md` 에 명시했다: **이 프로젝트의 운영
문서는 여기, 다른 프로젝트로 옮겨갈 지침은 `.guides/` 에 참조로.**

이 경계를 적어 두지 않으면 다음에 누군가 일반 가이드를 또 `docs/` 에 쓰고, 279가
막으려던 사본 드리프트가 그대로 재발한다.
